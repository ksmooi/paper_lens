# SaaS-Bench 論文導讀：Computer-Use Agent 在真實 SaaS 環境中的能力評估

## TL;DR

- SaaS-Bench 是一個基於 23 個真實、可部屬的開源 SaaS 系統建構的 CUA 評估基準，橫跨 6 個專業領域、包含 106 個長時距（平均 >100 步）任務
- 當前最強模型（Claude Opus 4.7）的 end-to-end resolved rate 僅 3.8%，Checkpoint Score 也只有 43.9%，暴露了規劃、狀態追蹤、跨應用上下文維護與錯誤恢復等根本性能力缺口
- SaaS-Bench 的關鍵洞察在於：將評估從簡化、孤立、短視野的合成環境轉移到真實 SaaS 工作流程，揭示了傳統 benchmark 系統性高估 CUA 能力的問題

## 背景與動機

### 從語言理解到行動執行：Computer-Using Agent 的崛起

大型語言模型（LLM）的發展，正經歷一場從「被動理解」到「主動執行」的典範轉移。傳統 LLM 的應用場景集中在語言理解與生成——問答、摘要、翻譯、程式碼撰寫——這些任務的輸入與輸出都是文字，模型不需要直接與外部世界互動。

Computer-Using Agent（CUA）的出現改變了這個格局。CUA 能夠直接操作真實軟體系統——瀏覽器介面、桌面 GUI、API——從而完成端到端的工作流程，例如資訊檢索、資料操作、多步驟任務執行。代表性系統包括 OpenAI 的 CUA（January 2025）、Anthropic 的 Computer Use（October 2024）、Ui-Tars（Qin et al., 2025）、OpenCUA（Wang et al., 2025）等。這些系統的核心思路類似：將 LLM 的輸出從純文字擴展為結構化的 UI 操作指令（點擊、輸入、導航），並通過持續的觀察-行動循環（perception-action loop）與環境互動。

然而，當一個領域從「理解」邁向「執行」，評估方式也必須跟著演進。在語言理解時代，評估的重點是模型知識的廣度與準確性——你可以在靜態的測試集上計算準確率。在 CUA 時代，評估的重點轉向模型在真實環境中的**行動能力**——能不能按對按鈕、能不能填對表格、能不能在多個應用之間切換協調、能不能從錯誤中恢復。

這個轉變看似自然，實則棘手。因為「行動能力」的評估遠比「理解能力」的評估複雜：它涉及環境的真實性、任務的複雜度、驗證的可靠性，以及跨應用的協調性。

### 現有 Benchmark 的系統性限制

為了評估 CUA 的能力，學界已經提出了多個 benchmark。SaaS-Bench 論文的 Table 1 對這些 benchmark 進行了系統性比較，並指出它們存在三個根本限制。

**第一，應用層級複雜度不足。**

即使是最先進的 web benchmark，其頁面邏輯、後端約束與狀態轉換也遠比真實 SaaS 系統簡單。WebArena（Zhou et al., 2023）建構了可執行的自架網站環境，但這些網站是為了基準測試而設計的，缺乏真實 SaaS 系統的業務邏輯深度、使用者認證流程、持久化狀態管理和跨頁面的動態依賴。Mind2Web（Deng et al., 2023）則基於離線的 human demonstration dataset，連執行的環境都沒有——agent 在靜態的頁面快照上操作，無法體驗操作的真實後果。OSWorld（Xie et al., 2024）雖然涵蓋了桌面級的操作場景，但其任務多為單一應用內的孤立操作。

更根本的問題是：這些 benchmark 的任務難度主要來自 UI 操作本身（找到正確的按鈕、填入正確的欄位），而非來自業務邏輯的深度。在真實 SaaS 系統中，一個「建立發票」的操作不僅需要填寫輸入框，還需要理解：發票的科目結構（什麼費用歸哪個科目）、稅務規則（不同產品的稅率）、客戶的信用額度、以及發票日期不應早於採購日期等業務約束。這些約束不存在於合成環境中。

**第二，缺乏真實的專業工作流程。**

真實的專業工作，從開立發票到員工入職流程，從 CRM 客戶管理到供應鏈協調，幾乎總是涉及跨系統協調與領域特定知識。然而，現有 benchmark 的任務通常被限制在單一應用的孤立場景中，目標也經過簡化。即使是最接近 SaaS 評估的 WorkArena（Drouin et al., 2024）和 WorkArena++（Boisvert et al., 2024），也只在 ServiceNow 單一平台上建構任務，無法評估跨應用協調能力——而跨應用協調恰恰是真實專業工作的核心特徵。

以一個真實的「員工離職結算」場景為例：HR 需要在 HRMS 中建立離職記錄，財務需要在 ERPNext 中進行薪資結算，CRM 管理者需要在 Twenty CRM 中將該員工的客戶重新分配。這三個操作分別涉及三個不同的 SaaS 系統，且彼此之間有資料依賴——HR 系統的離職日期決定了財務系統的薪資計算期間，客戶分配決定了 CRM 的任務排程。沒有任何一個現有 benchmark 能夠評估 agent 在這種跨系統依賴場景中的表現。

**第三，缺乏長時距依賴結構。**

**第三，缺乏長時距依賴結構。** 真實 SaaS 工作流程中，一個任務可能涉及超過 100 步操作，且前一步的輸出是後一步的輸入。這種長時距依賴對 agent 的規劃能力、狀態追蹤能力與錯誤恢復能力提出了嚴苛要求。現有 benchmark 大多只有 10–40 步的任務，無法暴露長時距場景下的失敗模式。SaaS-Bench 的實驗結果表明，隨著任務步數增加，所有模型的 checkpoint score 都呈現單調遞減的趨勢——這是短視野 benchmark 完全無法觀測到的現象。

SaaS-Bench 論文的結論是：現有 benchmark 系統性地高估了 CUA 的真實能力。Online-Mind2Web（Xue et al., 2025）的研究也呼應了這個結論——當從離線評估轉移到線上評估時，許多 agent 的表現大幅下降。這兩項獨立研究共同指向一個更根本的問題：**CUA 在受控環境中的表現，與在真實環境中的表現之間存在系統性偏差**。這個偏差的來源不僅是環境複雜度的差異，更是評估方法本身的限制。

### 為什麼 SaaS 環境是理想的評估場域

SaaS-Bench 的核心論證是：**SaaS（Software-as-a-Service）平台具備真實專業工作所需的三大關鍵特性，使其成為 CUA 評估的理想場域。**

第一，**複雜且真實的環境**。SaaS 系統具有完整的前後端邏輯、使用者認證、持久化資料庫、領域特定的業務約束。Agent 必須在真實的系統動態下操作，無法利用簡化環境中的捷徑。這比自架的玩具網站、靜態頁面快照或單一企業平台更能反映 agent 在真實場景中的實用性。

第二，**跨應用協調需求**。專業工作流程幾乎總是涉及多個 SaaS 系統的協作。以「員工離職結算」為例：你需要先在 HR 系統（如 BigCapital HRMS）建立離職記錄，在財務系統（如 ERPNext）進行薪資結算，在 CRM 系統（如 Twenty CRM）重新分配客戶案件。這些系統之間的資料依賴關係——共用客戶名稱、日期、金額——構成了對 agent 跨應用上下文維護能力的核心考驗。

第三，**固有的長時距任務結構**。SaaS 工作流程的天數級操作鏈（從建立記錄到審批到結算）意味著任務必然涉及長時距依賴。以 SaaS-Bench 的員工報銷任務（bof_023）為例，完整的 210 步操作涵蓋了從提交報銷申請、主管審批、財務驗證到付款記錄的全流程。每一步的輸出都影響後續步驟的輸入。

這三個特性——環境真實性、跨應用複雜度、長時距依賴——加在一起，使 SaaS 環境不僅是評估 CUA 能力的理想場域，更是暴露 CUA 在真實場景中根本限制的必要條件。從這個角度來看，SaaS-Bench 的價值不僅在於它是一個新的 benchmark，更在於它將 CUA 評估從「實驗室條件」推向了「現場條件」——就像自動駕駛評估從封閉賽道轉向開放道路一樣。

### SaaS-Bench 的任務統計分析

SaaS-Bench 包含 106 個任務，其統計數據從多個維度揭示了任務的複雜性：

**多模態分布**：74 個文字型任務（70%）與 32 個多模態任務（30%）。多模態任務主要集中在農業（照片辨識）與媒體（圖片編輯）領域，這反映了這兩個領域的工作流程天然依賴視覺資訊。

**跨應用分布**：只有 7 個任務（6.6%）涉及單一應用；26 個任務（24.5%）涉及兩個應用；53 個任務（50.0%）涉及三個應用；20 個任務（18.9%）涉及四個應用。這意味著 93.4% 的任務需要 agent 在多個應用之間協調操作。

**操作長度分布**：從 Claude Opus 4.6 的執行軌跡估計，72/74 個文字型任務（97.3%）超過 100 步門檻，19/32 個多模態任務（61.3%）超過 100 步。最長的任務可達 350–400 步。這份分布確認了 SaaS-Bench 的長時距特性並非誇大——它確實要求 agent 在數百步的操作中維持規劃、狀態追蹤與錯誤恢復能力。

## 核心知識點

### 知識點 1：CUA 領域的前世今生

在深入 SaaS-Bench 之前，有必要先理解 CUA（Computer-Using Agent）這個領域的發展脈絡。

CUA 的核心概念非常直觀：讓 LLM 不僅能「說」，還能「做」。傳統 LLM 的輸入是文字、輸出也是文字；CUA 的輸入是文字（任務描述）+ 環境狀態（網頁截圖、DOM 樹、Accessibility Tree），輸出則是對環境的操作指令（點擊某個按鈕、在輸入框鍵入文字、導航到某個 URL）。

這個看似簡單的改變，實際上涉及了一系列深層挑戰：

- **感知**：Agent 需要理解當前的 UI 狀態。這可以透過 HTML DOM、Accessibility Tree、螢幕截圖或它們的組合來實現。不同的感知方式各有優劣——DOM 提供結構化資訊但缺乏視覺布局；截圖保留視覺布局但需要 VLM 的理解能力
- **推理**：Agent 需要根據任務目標與當前狀態決定下一步該做什麼。這涉及規劃（將大任務分解為子步驟）、決策（在多個可行操作中選擇）、以及狀態追蹤（記住已完成的子任務與尚未滿足的依賴）
- **行動**：Agent 需要精確地執行目標操作——點擊正確的按鈕、在正確的欄位中輸入正確的值、上傳正確的檔案。這看起來簡單，但在複雜的 SaaS UI 中，兩層選單、動態載入的內容、非同步表單驗證，都使得操作的精確執行遠比看起來困難
- **驗證**：操作執行後，Agent 需要確認操作是否生效。這涉及重新讀取頁面狀態、比對期望輸出與實際結果——而正如 SaaS-Bench 揭示的，當前 CUA 在這環節存在系統性缺陷

CUA 評估的難度，就在於需要同時衡量這四個環節的能力。大多數現有 benchmark 只關注「推理」與「行動」，忽略了「感知」與「驗證」——而 SaaS-Bench 的實驗結果表明，後兩個環節恰恰是當前 CUA 的最大瓶頸。

### 知識點 2：CUA Benchmark 的設計空間

CUA benchmark 的設計需要在五個維度上取得平衡，而這些維度構成了一個完整的設計空間：

1. **環境真實性（Environment Realism）** ：從合成靜態頁面（MiniWoB++）到真實可部署 SaaS 系統（SaaS-Bench），環境越真實，評估結果越能反映實際部署能力
2. **跨應用範圍（Cross-Application Scope）** ：從單一應用（WorkArena++ 只限 ServiceNow）到跨多個獨立系統（SaaS-Bench 涉及 23 個獨立 SaaS）
3. **任務視野長度（Task Horizon）** ：從短時距（10–30 步）到長時距（>100 步），長視野任務更考驗規劃與狀態追蹤
4. **驗證可靠性（Verification Reliability）** ：從依賴 LLM-Judge 到多重驗證機制（資料庫查詢、API 檢查、正則匹配）
5. **可擴展性（Scalability）** ：人工設計 vs LLM 輔助合成 vs 全自動生成，不同方法在成本與品質之間權衡

SaaS-Bench 在 1–4 維度上都達到最高水準，但在第 5 維度上仍依賴 LLM + 人工審查的混合模式。

### 知識點 2：真實 SaaS 環境 vs 合成環境的關鍵差異

真實 SaaS 環境與合成或簡化環境之間存在一些難以複製的關鍵差異：

- **前後端完整互動**：每個按鈕點擊都觸發真實的後端處理、資料庫寫入、狀態更新。合成環境常常只做前端模擬，缺乏後端約束
- **業務邏輯深度**：真實 SaaS 系統有複雜的欄位驗證規則、審批流程、權限控制、業務規則（例如「發票日期不可晚於付款日期」）
- **動態狀態管理**：系統狀態會隨著操作持續演變，且操作效果可能因非同步處理、客戶端快取、UI 狀態不同步而延遲生效
- **領域特定術語**：CRM 中的 account/contact/lead 區分、會計中的借方/貸方、醫療中的 ICD-10 編碼——agent 需要理解這些領域概念才能正確操作
- **非同步處理的不可預測性**：後端處理有延遲，頁面載入需要等待，操作結果不一定立即反映在 UI 上

這些差異意味著：在合成環境中表現良好的 agent，在真實 SaaS 環境中可能完全無法運作。

### 知識點 3：SaaS-Bench 的三項設計原則

SaaS-Bench 的架構建立在三項設計原則之上：

**原則一：真實且可部署的 SaaS 環境。**

SaaS-Bench 不是提供 API 或模擬器，而是提供 23 個完整的、可獨立部署的開源 SaaS 系統。這些系統以 Docker 容器化，可在本地部署並透過瀏覽器存取。每個系統都經過領域專家審查，確保其功能與填入資料反映真實專業使用場景。部屬前會先進行語義資料填充——分析 SQL schema、頁面結構、欄位語意與業務邏輯——使用 LLM 生成逼真的偽資料，或在適當情況下導入開源資料集。

**原則二：組合式、跨應用的專業工作流程。**

任務不是隨機組合多個應用，而是從專業角色與工作流程種子出發，建構出具有業務連貫性的跨系統工作流程。SaaS-Bench 的任務涵蓋六個專業領域：軟體工程與專案管理、商業運營與財務、醫療保健管理、團隊協作與文件工作流、手工農業食品供應鏈、獨立媒體創作。99/106 個任務（93.4%）涉及至少兩個應用，其中三個應用的任務最多（53 個，50.0%）。

**原則三：長時距任務結構。**

任務平均操作步數超過 100 步。97.3% 的文字型任務與 61.3% 的多模態任務超過 100 步門檻。這種設計確保 benchmark 能夠評估 agent 在長時間執行中的規劃、狀態管理與錯誤恢復能力。

### 知識點 4：Builder-Challenger-Refiner 任務合成管線

SaaS-Bench 的任務不是隨機生成的，而是經過一套嚴謹的四階段管線：

**Stage I — Task Seed and Role Definition**：從六個專業領域出發，為每個領域定義代表性職業角色（如專案經理、財務人員、醫療管理者、供應鏈協調員、媒體創作者），將其日常工作流程抽象為任務種子。

**Stage II — Task Synthesis Loops**：使用 LLM（論文使用 Claude Opus 4.6）作為 Builder，Human Expert 作為 Challenger 和 Refiner，對每個候選任務進行迭代式審查。Challenger 檢查任務描述的明確性、完整性、可執行性與可驗證性；Refiner 決定接受、退回或附帶修改指示。這個循環持續直到任務通過審查或達到最大迭代次數。

**Stage III — Static Check**：所有候選任務通過靜態品質檢查，評分涵蓋六個維度（專業性、跨應用自然度、依賴深度、可驗證性、敘事連貫性、複雜度品質），並標記三種反模式（CRM dumping ground、平行任務、規格溢出）。

**Stage IV — Execution Check**：人類專家實際執行每個任務，檢查任務-驗證器對齊度、失敗歸因與指令清晰度。

最終只有 45% 的候選任務通過完整審查流程。

### 知識點 5：SaaS-Bench 的 23 個系統與六個專業領域

SaaS-Bench 選擇的 23 個 SaaS 系統不是隨機挑選的。論文設定了三個選擇標準：(1) 必須是真實的應用軟體，具備完整的前後端邏輯、使用者認證、持久化資料庫與領域特定業務約束；(2) 必須涵蓋廣泛的專業場景；(3) 必須有跨應用工作流程的潛力，讓功能互補的應用可以自然地組合為多系統任務。

六個領域及其包含的系統如下：

**Software Engineering and Project Management（軟體工程）**：包含 OpenProject（專案管理）、Baserow（低程式碼資料庫）、Code-Server（雲端開發環境）、Metabase（資料分析與儀表板）。任務示例：在 OpenProject 建立專案計畫，在 Baserow 建立需求追蹤表，在 Metabase 建立進度儀表板。

**Business Operations and Finance（商業運營與財務）**：包含 BigCapital（財務會計）、Twenty CRM（客戶關係管理）、ERPNext（企業資源規劃）、Pretix（票務與活動管理）、HRMS（人力資源管理）。任務示例：從建立發票、主管審批、會計入帳到客戶付款確認的完整報銷流程。

**Healthcare Administration（醫療保健管理）**：包含 OpenEMR（電子病歷系統）、OpnForm（表單建構工具）、OnlyOffice（文書處理）。任務示例：完成 SOAP 病歷記錄、應用 ICD-10 診斷編碼、生成正式病例報告並建立公共衛生通報表單。

**Team Collaboration and Document Workflow（團隊協作與文件工作流）**：包含 ownCloud（檔案同步與共享）、Mattermost（即時通訊）、OnlyOffice（協作編輯）、SiYuan（知識管理與筆記）。任務示例：建立團隊知識庫文件並透過 Mattermost 頻道發布公告。

**Artisan Agri-Food Supply Chain（農業食品供應鏈）**：包含 FarmOS（農場管理）、Grocy（家庭庫存管理）、Recipya（食譜管理）、Roundcube（電子郵件）。任務示例：從收穫記錄登錄、庫存更新到客戶訂單建立的完整供應鏈追蹤。

**Independent Media Creation（獨立媒體創作）**：包含 PhotoPrism（照片管理與 AI 標籤）、MediaCMS（媒體內容管理）、BookLore（書籍管理）、Watcharr（媒體追蹤）、E-Label（標籤管理）。任務示例：從相機照片導入、AI 自動標籤、編輯調整到媒體庫發布的完整工作流程。

每個系統在部署前都經過語義資料填充（Semantic Data Population）：先匯出 SQL schema 並分析頁面結構、欄位語意與業務邏輯，然後使用 LLM 生成逼真的偽資料，或在有適當開源資料集的情況下導入。以 OpenEMR 為例，系統中預先建立了多筆虛擬病患記錄、ICD-10 診斷代碼與預約時間表。這些措施確保 agent 的表現反映的是真實互動能力而非環境的人為痕跡。

### 知識點 6：加權檢查點驗證體系

SaaS-Bench 的評估協議採用三層驗證與兩種指標：

**三種驗證類型**：

1. **State-Check**：驗證客觀系統狀態，包含五個子類型：
   - DB-Check：查詢資料庫確認記錄、欄位或關聯存在
   - API-Check：呼叫後端 API 確認系統狀態
   - Numeric-Threshold-Check：驗證數值在指定容差範圍內
   - File-System-Check：檢查檔案存在性、格式或內容
   - Email/Message-Check：驗證郵件正確發送

2. **Content-Check**：驗證文件或文字輸出，包含：
   - Regex/String-Match：正則表達式或精確字串比對
   - Doc-Extraction-Check：從文件中提取結構化內容並驗證

3. **LLM-Judge**：評估開放式輸出，包含文字與 VLM 評判

**兩種指標**：

- **Resolved Score**：所有檢查點通過 = 1，否則 = 0。這是嚴格指標，反映任務的完整完成率
- **Checkpoint Score**：基於通過檢查點的加權部分分數。這才是論文認為更公平的指標，因為長時距任務中即使最終沒完成，過程中也能累積大量進度

**Agent 行動空間**包含 22 個操作（22 actions），分為三類：瀏器 UI 操作（click、input、navigate、scroll 等）、檔案系統操作（read/write/replace file）、終止操作（done）。值得注意的是，`evaluate`（原始 JavaScript 執行）被刻意禁用，以保持行為可重現性。

### 知識點 6：SaaS-Bench 的語義資料填充與 Docker 部署

SaaS-Bench 的一個被低估的工程貢獻是其語義資料填充（Semantic Data Population）流程。

一個空的 SaaS 系統（如剛安裝的 OpenEMR）是無法直接用於評估的——它沒有病患記錄、沒有診斷代碼、沒有預約時間表。Agent 在這樣的空系統中無法執行任何有意義的任務。SaaS-Bench 解決這個問題的方法是：先匯出每個系統的 SQL schema，分析網站結構、頁面佈局、欄位語意與業務邏輯，識別出關鍵的實體、欄位與關聯。

然後採用兩種互補的策略：對於沒有合適公開資料來源的系統，使用 LLM 根據 schema 與網站功能生成逼真的偽資料；對於有適當公開資源的場景，則導入開源資料集以產生更自然的資料分布。以 FarmOS（農業管理）為例，它可能導入了公開的農作物種植資料；以 OpenEMR 為例，它可能使用 LLM 生成了一批虛擬病患的病歷記錄。

部署方面，所有 23 個系統都透過 Docker 容器化，並暴露為可透過瀏覽器存取的服務。每次任務執行前，環境被重置到預先定義的初始狀態，防止任務之間的狀態污染。系統版本、設定檔、種子資料與啟動腳本都被鎖定，確保同一任務可以在完全相同的初始條件下重複執行。

### 知識點 7：WorkArena++ 的方法與貢獻

WorkArena++（Boisvert et al., 2024）是 SaaS-Bench 最直接的前置工作，由 ServiceNow Research 發表於 NeurIPS 2024。其核心貢獻包括：

**三層難度架構**：

- **L1（原始 WorkArena）** ：33 個原子級任務，如填寫單一表格、排序列表，但缺乏複合推理需求
- **L2（Explicit）** ：341 個複合任務，agent 收到明確的操作步驟指示
- **L3（Ticket + KB）** ：相同的 341 個工作流程，但指令透過 ServiceNow 的 ticket 機制與知識庫文章提供

**五種技能類別**（涵蓋 682 個任務）：

1. **Planning and Problem Solving**（66 × 2）：如工作排程、員工工作量分配
2. **Information Retrieval**（39 × 2）：從儀表板或列表中提取資訊
3. **Data-driven Decision Making and Reasoning**（156 × 2）：如投資組合選擇（knapsack 問題）
4. **Sophisticated Memorization**（28 × 2）：如員工入職流程中的多頁資訊記憶
5. **Contextual Understanding through Infeasible Tasks**（52 × 2）：識別不可執行任務

**核心局限**：所有任務局限在 ServiceNow 單一平台，缺乏跨應用協調；任務視野相對較短（Oracle 操作數遠低於 SaaS-Bench 的 >100 步）；缺乏多模態任務。

### 知識點 8：SaaS-Bench 的實驗結果

論文評估了 14 個先進模型，實驗結果揭示幾個關鍵發現。

**平均操作步數分析。** 不同模型在完成任務時所需的平均操作步數差異顯著。Claude Opus 4.7 在平均 175 步內完成任務，是所有模型中最有效率的；Claude Sonnet 4.6 只需 155 步，但得分較低（27.1%）。Doubao Seed 2.0 Pro 需要最多的 324 步，但得分只有 34.1%。這說明操作效率與任務表現之間沒有簡單的相關性——有些模型走捷徑卻做錯了，有些模型做了很多但沒有做對。

**總體表現極低**：最強模型是 Claude Opus 4.7，Resolved Rate 僅 3.8%，Checkpoint Score 43.9%。其次是 GPT-5.5 High（1.9% / 43.8%）與 Claude Opus 4.6（1.9% / 43.2%）。這三款模型在總體 checkpoint score 上非常接近（43.9%、43.8%、43.2%），但 resolved rate 的差異（3.8% vs 1.9%）說明了 checkpoint score 相近的模型可能在 end-to-end 完成能力上有本質差距。

**領域差異顯著**：模型在 Business（財務、CRM）領域表現最好（Opus 4.7 達 31.8%），Healthcare 次之（29.7%），Media 領域最差（即使 Opus 4.7 也僅 10.9%）。這反映了多模態任務對當前 CUA 的額外挑戰。有趣的是，GPT-5.5 High 在 Business 領域（36.4%）超越了 Opus 4.7（31.8%），但在 Software Engineering 領域（45.8%）遠遠落後於 Opus 4.7（52.9%）。這表明不同模型的優勢領域不同，總體排名可能掩蓋了重要的領域性差異。

**單調性能衰減（Monotonic Performance Decay）** ：所有模型都呈現隨著任務進展而持續衰退的趨勢。這種衰退不是偶發的，而是系統性的——當任務超過 50 步後，agent 的錯誤率穩定增加。論文將此歸因於累積誤差：早期的小錯誤（例如填錯一個欄位）會在長時距任務中不斷放大，最終導致任務失敗。

**pass@k 分析**：pass@1 嚴重低估了某些模型的真實能力。例如 pass@5 有時比 pass@1 高出 2–3 倍，顯示模型其實具備完成任務的潛力，但單次運行的隨機性讓它無法穩定展現。這意味著報告 pass@1 的 benchmark（包括許多既有工作）可能系統性地低估了 CUA 的潛力。

**pass@1 的誤導性**：另一面，pass@1 也可能高估——同一個模型的多個 runs 之間的方差極大。以 bof_023 任務為例，Qwen 3.6 Plus 在 Run 0 得 0.80，Run 2 卻掉到 0.10，而在這個任務上 Gemini 3.1 Pro 呈現完全相反的方差模式。論文因此建議未來 CUA 評估應至少報告 pass@3 或 pass@5，並附上方差資訊。

**所有模型的共同弱點**：儘管模型之間存在能力差距，但它們在幾個面向上的弱點是一致的：跨應用導航後的上下文遺失、填寫多欄位表單時的欄位混淆、以及無法從錯誤中恢復。這暗示了這些弱點可能來自 CUA 架構的共性缺陷（如 browser-use 的行動空間設計、LLM 的注意力機制限制），而非特定模型的問題。

### 知識點 8：SaaS-Bench 發現的關鍵失敗模式

論文在 §5 深入分析了三種關鍵失敗模式，這些模式在短視野 benchmark 中不易被發現：

**模式一：級聯式資源耗盡（Cascading Resource Exhaustion）**

以 bof_133 任務為例，agent 需要在三個 SaaS 系統中協調：BigCapital（財務）、ERPNext（會計）、Twenty CRM（客戶關係）。任務超過 200 步。失敗模式是典型的級聯效應：agent 花太多時間在第一個系統的操作上（例如錯誤導航導致多餘的點擊），消耗了操作步驟預算，導致後續系統的操作被倉促完成或直接跳過。即使在過程中意識到時間不足，也無法有效調整策略。

**模式二：瓶頸點錯誤（Chokepoint Errors）**

以 bof_019 任務為例，Agent 需要在 BigCapital 中建立一個公司客戶（Arcturus Digital）並完成採購付款流程。關鍵的瓶頸點是：BigCapital 區分「個人客戶」和「公司客戶」兩種實體類型，透過一個顯示名稱選擇器來選擇。Agent 若同時填入個人姓名（Elena Vasquez）和公司名稱（Arcturus Digital），系統會預設為個人客戶。這個錯誤無法在執行中被檢測——資產負債表顯示「Elena Vasquez (Arcturus Digital)」與預期的 $55,000 金額，agent 將其解讀為正確完成。但驗證時查詢「Arcturus Digital」卻找不到任何資料。這個錯誤影響了 30% 的任務分數。

**模式三：缺乏閉環驗證（Absent Closed-Loop Verification）**

以 bof_023 任務為例，Claude Opus 4.6 在 210 步的操作中，於第 124 步正確識別出發票日期錯誤（2026-03-19 應為 2026-03-20），並規劃了修正。但 86 步後，agent 的評估竟轉為「成功」，終止時自信地宣稱「Bill created dated 2026-03-20」。驗證結果顯示日期仍是 2026-03-19。論文指出這暴露了兩層問題：(1) Agent 在修正後沒有重新驗證——人類會重新載入頁面、重新讀取欄位來確認修正生效，但 agent 直接跳到下一個子任務；(2) Agent 的終止總結似乎從規劃中的意圖而非實際觀察到的執行結果中提取資訊。

### 知識點 9：單次運行的可靠性問題（pass@1 的陷阱）

論文在 §5.4 深入分析了同一個模型在同一個任務上多次運行的方差問題。

**案例：Claude Sonnet 4.6 on bof_155**。三次運行分別得到 0.000、0.214、0.679——從「完全失敗」到「實質完成」，差距是質性的而非僅是量性的。這種方差無法歸因於環境隨機性，因為每次運行都在完全相同的初始狀態下開始。

**案例：Cross-Model Divergence on bof_023**。Qwen 3.6 Plus 在三次運行中得到 0.80、0.70、0.10，而 Gemini 3.1 Pro 得到 0.10、0.10、0.70——兩個模型呈現相反的方差模式。

**根本原因：Bifurcation Points 與路徑依賴。** 長時距 SaaS 工作流程中，在關鍵決策點（選擇先進入哪個應用、解讀歧義欄位、決定重試或放棄）上的微小差異，會導致完全不同的執行軌跡。一旦 agent 走上次優路徑（例如在 bof_155 中花 50 步在一個不熟悉的 UI 元素上），剩餘的步驟預算可能不足以恢復。

**實務意涵**：(1) 對於評估，僅報告 pass@1 可能有嚴重誤導——單次運行可能高估或低估模型能力；(2) 對於部署，生產環境的 CUA 系統需要重試機制、集成策略或基於檢查點的恢復機制。

## 從 WorkArena++ 到 SaaS-Bench 的演進脈絡

### WorkArena++ 的定位：企業 SaaS 評估的第一步

WorkArena++ 是首個聚焦於企業知識工作場景的 CUA benchmark。它的核心設計哲學是：在 ServiceNow——這個 Fortune 500 中 85% 的公司使用的企業平台——上建構真實的工作流程任務。

WorkArena++ 整合在 **BrowserGym**（Drouin et al., 2024）框架中。BrowserGym 是一個標準化的 gym environment，提供了 chat-based agent-human interaction、enriched multimodal observations（HTML、accessibility tree、screenshot、element coordinates）、以及標準化且靈活的行動空間。它支援多個 web agent benchmark，包括 MiniWob、WebArena 與 WorkArena。SaaS-Bench 雖然沒有直接使用 BrowserGym，但使用了類似的 browser-use 執行框架。

WorkArena++ 的任務涵蓋五種技能類別，其中「Infeasible Tasks」（52 × 2 個任務）是一個特別有趣的設計——它要求 agent 能夠辨識哪些任務是無法完成的（例如填寫不存在的欄位），並通過 chat 通知使用者。這測試的是 agent 在面對不確定性時的行為，而不僅僅是操作能力。

WorkArena++ 的 Oracle trace 提取機制也很值得一提：每個任務都有一個用 Playwright 編寫的 oracle 函數，可以自動生成完整的 gold trajectory（screenshot + axtree + action），這使得使用這些資料進行模型微調成為可能。SaaS-Bench 也使用了類似的 oracle 機制（verify.py），但 focus 是驗證而非生成 gold trajectory。

在 L2（Explicit）與 L3（Ticket + KB）的難度設計上，WorkArena++ 引入了兩個重要的概念：(1) 任務的「明確性」是一個連續光譜，從明確步驟指示到模糊的 ticket 描述；(2) 真實的工作流程中，知識工作者經常需要從多個來源（ticket + 知識庫）整合資訊才能完成任務。L3 的設計要求 agent 先讀取 ticket 理解任務目標，再導航到知識庫文章找到操作步驟，然後執行——這比直接給出步驟指令的 L2 更真實，也更困難。

然而，L3 的實作有一個潛在的弱點：知識庫文章的內容實際上就是 L2 的步驟指示。這意味著 L3 任務的真正挑戰在於「找到正確的知識庫文章」而非「從模糊描述中推理出所需步驟」。在真實場景中，知識工作者通常只有模糊的目標描述，需要自己推導出所需的操作步驟——而 WorkArena++ 的 L3 在這個意義上仍然偏簡單。

### WorkArena++ 的關鍵局限

然而，WorkArena++ 存在三個根本性的限制，這些限制也是 SaaS-Bench 試圖解決的核心問題：

**第一，單一平台限制。** WorkArena++ 的所有任務都在 ServiceNow 平台上執行。這意味著 agent 永遠不需要處理跨系統協調——不需要在不同 CRM、HR 與財務系統之間切換，不需要記住多個系統的登入憑證與 API 行為差異。論文自身也在 §G.1 討論了這個限制，但將其辯護為「UI 組件在各企業平台之間是通用的」。然而這個推理在 SaaS-Bench 的實驗結果面前顯得脆弱：SaaS-Bench 的跨應用任務（93.4% 的任務涉及跨應用）暴露了 agent 在系統切換時的顯著困難。

**第二，任務視野較短。** WorkArena++ 的大多數任務在 20–60 步 Oracle 操作內可以完成，遠低於 SaaS-Bench 平均 >100 步的操作數。這使得 WorkArena++ 無法暴露長時距任務特有的失敗模式——級聯效應、累積誤差、路徑依賴。

**第三，缺乏多模態任務。** WorkArena++ 的任務全部基於文字型 UI（ServiceNow 的標準介面），不涉及真實世界中的圖片、PDF、文件、媒體資產等模態。然而真實的專業工作流程中，這些模態是無所不在的：醫療影像、發票掃描、產品照片、會議記錄 PDF。

這個表格凸顯了 SaaS-Bench 的獨特定位：它是唯一同時滿足真實性、專業性、跨應用、長時距與多模態五個維度的 CUA benchmark。但也值得注意的是，SaaS-Bench 的任務總數（106）遠少於 WorkArena++（682），原因是其任務建構流程更加嚴謹（僅 45% 通過審查），每個任務的複雜度也更高。

### SaaS-Bench 的突破性設計

SaaS-Bench 在三個方面實現了對 WorkArena++ 的突破：

**從單一平台到多元 SaaS 生態系。** SaaS-Bench 選擇了 23 個來自不同供應商、不同領域的獨立開源 SaaS 系統，而不是依賴單一企業平台。每一個系統都有完整的業務邏輯、使用者認證與資料庫——agent 必須像真實的使用者一樣，在不同系統之間切換操作。這使得 SaaS-Bench 能夠評估 agent 的「跨應用上下文維護能力」：當 agent 在 BigCapital 建立發票時，需要記得在 Twenty CRM 中已經建立的公司客戶名稱；當從 OpenEMR 切換到 OpnForm 時，需要記得前一系統中記錄的診斷結果。

**從短視野到長時距任務。** SaaS-Bench 的平均任務操作數超過 100 步，最長的任務可達 400 步以上。這使得評估能夠捕捉短視野環境中不可見的失敗模式——尤其是「級聯式資源耗盡」與「瓶頸點錯誤」，這些模式在 20–60 步的任務中幾乎不可能出現。

**從純文字到多模態。** SaaS-Bench 包含 32 個多模態任務（佔總數的 30%），涵蓋農業（照片辨識）與媒體（圖片編輯）領域。這填補了 WorkArena++ 完全缺乏多模態評估的空白。

### 任務合成管線的詳細比較

SaaS-Bench 與 WorkArena++ 在任務建構方法上有根本性的差異。

WorkArena++ 的任務是透過組合低層次原子任務建構的。每個原子任務（L1）對應一個特定的 UI 操作模式（填表、排序、過濾等），高層次任務（L2、L3）則由多個原子任務序列組合而成。這種方法具有很強的可擴展性：一旦建立了原子任務庫，組合出新任務的成本很低。但缺點是任務的「專業真實感」取決於原子任務的覆蓋範圍——如果某個專業工作流程涉及原子任務庫未涵蓋的操作模式，就無法被準確建模。

SaaS-Bench 則採用了完全不同的方法。它的任務不是從原子操作組合而成的，而是從專業角色與工作流程種子出發，以「由上而下」的方式建構。Builder-Challenger-Refiner 管線確保每個任務都具有專業深度與業務連貫性，但這種方法的可擴展性較低——每個任務都需要多輪人工審查，最終只有 45% 的候選任務通過審查。

這兩種方法的取捨反映了 CUA benchmark 設計中的一個基本張力：**可擴展性 vs 真實性**。WorkArena++ 選擇了可擴展性（682 個任務），SaaS-Bench 選擇了真實性（106 個任務，但每個都經過嚴格驗證）。理想的 CUA benchmark 可能需要結合兩者的優點：使用 LLM 驅動的生成管線提高可擴展性，同時加入嚴格的自動化驗證（而非人工審查）來確保品質。

### 驗證機制的演進

SaaS-Bench 引入了比 WorkArena++ 更先進的加權檢查點驗證體系。WorkArena++ 使用二元成功/失敗驗證（每個任務一個 oracle + 一個 validator），而 SaaS-Bench 使用多個加權檢查點，可以衡量部分進度。

這裡值得深入討論一下三種驗證方法的適用場景：

**State-Check** 是最可靠的驗證方式，因為它直接查詢系統的持久化狀態（資料庫記錄、API 回應），不受 UI 渲染差異的影響。例如要驗證「發票是否已建立」，最好的方式是查資料庫確認發票表中確實存在該筆記錄，而非檢查瀏覽器中是否顯示了發票頁面。State-Check 的缺點是實現成本高——每個任務需要設計對應的查詢邏輯。

**Content-Check** 適合驗證文件類的輸出——報告內容、郵件正文、表單輸出。透過 regex 或 string matching，可以精確比對關鍵欄位值。但這要求預先知道期望的輸出格式，對開放式寫作任務的驗證力較弱。

**LLM-Judge** 是最靈活但也最不可靠的驗證方式。它適用於無法用規則驗證的開放式輸出——報告品質、圖像理解結果。但 LLM-Judge 引入了驗證器本身可能存在的偏誤：不同 LLM 對同一份報告的評分可能不同，同一個 LLM 在不同時間對同一份報告的評分也可能不同。SaaS-Bench 透過將 LLM-Judge 僅用於開放式任務、並搭配 State-Check 與 Content-Check 作為主要驗證方式，來控制這個風險。

### 知識點 7：SaaS-Bench 的實驗設置

SaaS-Bench 的實驗設置有幾個值得注意的設計選擇：

**執行框架**：使用 browser-use（Müller & Prijon, 2024）作為統一的執行框架。所有 agent 僅能透過瀏覽器 UI 操作（點擊、輸入、導航、讀取頁面內容）與環境互動，不允許直接存取資料庫、後端 API、檔案系統或任務驗證器。這個限制確保了評估的公平性——agent 必須像人類使用者一樣操作 UI，無法走後門捷徑。

**環境重置**：每次任務執行前，對應的 SaaS 環境被重置到預先定義的初始狀態。這確保了不同模型、不同 runs 之間的比較是在完全相同條件下進行的。

**模型評估**：論文評估了 14 個先進模型，包含 Claude Opus 4.7/4.6/4.5、GPT-5.5/5.4 High、Kimi K2.6/K2.5、Qwen 3.6 Plus、Gemini 3.1 Pro/3.5 Flash High、Doubao Seed 2.0 Pro、DeepSeek V4 Pro、GLM-5.1、MiniMax M2.7，以及 Claude Sonnet 4.6。每個 agent 只收到任務描述、應用入口 URL 與登入憑證——不提供參考步驟。

**指標選擇的考量**：論文同時報告 Resolved Score 與 Checkpoint Score 的原因，在於後者比前者更能反映 agent 在長時距任務中的真實進展。一個 agent 可能完成了 90% 的操作（通過了 10 個檢查點中的 9 個），但在最後一步出錯——Resolved Score 會給出 0%，而 Checkpoint Score 給出 90%。兩者都是重要的訊號。在 SaaS-Bench 這樣的困難 benchmark 中，Checkpoint Score 比 Resolved Score 提供了更多的資訊量。

關鍵觀察點：

**Resolved Score 極低。** 所有模型的 end-to-end resolved rate 都低於 4%。Claude Opus 4.7 以 3.8% 居冠，GPT-5.4 High 也達到 3.8%，但其他模型都只有 0–1.9%。這個結果意味著：當前的 CUA 幾乎無法獨立完成任何一個完整的、跨應用的 SaaS 工作流程。

**Checkpoint Score 提供了更豐富的資訊。** 雖然 Resolved Score 極低，但 Checkpoint Score 的範圍在 15.8–43.9% 之間。這表示模型能夠完成部分工作流程，但幾乎無法完成完整的端到端任務。Claude Opus 4.7 的 43.9% 遠高於倒數的 MiniMax M2.7 的 15.8%，顯示模型之間的確存在顯著能力差距。

**領域差異巨大。** 所有模型在「軟體工程」領域的表現都是最高的（Opus 4.7 達 52.9%），在「媒體」領域的表現都是最低的（同一個模型僅 10.9%）。這反映了多模態任務對當前 CUA 的額外挑戰——媒體領域的任務涉及圖片處理與視覺內容創作，需要 VLM 能力而不僅是 UI 操作能力。

**模型規模與表現的相關性不強。** GPT-5.5 High 的 Checkpoint Score（43.8%）與 Claude Opus 4.7（43.9%）幾乎相同，但平均步數卻從 175 增加到 200。Claude Opus 4.6（257 步 / 43.2%）花了更多步驟卻沒獲得更好的分數。這暗示了長時距任務中的效率問題：更多步驟不等於更好的結果，有時反而是低效規劃的訊號。

### 表現隨任務進展的單調衰減

論文在 §4.3 中報告了一個重要發現：所有模型的性能都隨任務進展而單調衰減。具體來說，將任務分成前中後三段，模型在最後三分之一的 Checkpoint Score 平均比前三分之一低 30–40%。這種衰減是系統性的，不是模型特定的。

**衰減的量化分析。** 將一個 200 步的任務分為四個 quartile（每 50 步為一段），模型在前 50 步的檢查點通過率約為中段的 1.5 倍，為末段的 2–3 倍。這意味著 agent 在任務初期表現最好，但隨著任務進展，錯誤率穩定增加。

**衰減的幾種可能原因。** 論文指出了三個可能的機制：

1. **累積誤差傳播（Cumulative Error Propagation）** ：早期的小錯誤會影響後續所有依賴該步驟的檢查點。一個在步驟 20 時不小心填錯的欄位值，可能會在步驟 150 時仍然影響最終結果。隨著任務步數增加，未被修正的早期錯誤數量線性增長

2. **注意力衰退（Attention Decay）** ：LLM 的上下文注意力在長序列中會自然衰退。當 agent 的操作軌跡超過數百步時，早期的任務描述、系統狀態與操作結果在注意力中的權重會逐漸降低，導致 agent 忘記了任務的約束條件或早期已完成的步驟

3. **決策疲勞（Decision Fatigue）** ：隨著任務步數增加，agent 可能需要做出更多決策，但每一步的決策品質可能會下降。這在 bof_155 案例中表現得很明顯：agent 在後半段開始跳過驗證步驟，直接假設操作成功

**與 WorkArena++ 的對比。** WorkArena++ 的任務多數在 20–60 步內完成，因此不會觀察到這種衰減模式。在短視野任務中，累積誤差的效應不明顯，因為錯誤還沒有足夠的距離來放大。這再次突顯了長時距評估的必要性。

這種衰減的根本原因是長時距任務中的誤差累積：在 200+ 步的操作中，早期的小錯誤（如點錯欄位、填錯格式）會影響後續所有步驟的正確性。更糟的是，agent 往往無法意識到這些錯誤已經發生，因此不會嘗試修正。

### WorkArena++ 的實驗結果

WorkArena++ 的實驗同樣顯示當前 CUA 能力不足，但程度輕微得多。最佳模型（GPT-4o + SoM prompting）在 L2 上達到約 35% 的成功率，L3 上約 20%。

SaaS-Bench 與 WorkArena++ 的實驗結果之間的差距不能用「模型差距」來解釋——SaaS-Bench 評估的是 2026 年初的先進模型，理論上應比 2024 年的模型更強大。這個差距只能歸因於 SaaS-Bench 的評估環境更真實、任務更困難。

**為什麼差距這麼大？** 主要原因有三個：

1. **任務複雜度差異**：WorkArena++ 的任務雖然需要規劃與推理，但仍在 ServiceNow 單一平台上執行。Agent 不需要記住另一個系統的登入憑證、不需要理解另一個系統的 UI 佈局、不需要在不同系統的資料模型之間進行對映。SaaS-Bench 的跨應用需求使任務本質上更困難

2. **任務視野差異**：WorkArena++ 的大多數任務在 20–60 步內完成，而 SaaS-Bench 的平均步數超過 100 步。長時距任務中的累積誤差從數學上保證了 Resolved Score 的低落

3. **評估指標差異**：WorkArena++ 使用二元成功/失敗驗證（每個任務一個 oracle + 一個 validator），而 SaaS-Bench 使用多個加權檢查點。若 SaaS-Bench 也使用二元驗證，其 Resolved Score 可能更低

**WorkArena++ 的錯誤分析**也提供了有價值的對比。該論文 §F 列出以下錯誤類型：

- **Bid 混淆**：Agent 錯誤地將 iframe 內元素的 bid 記為一般元素的 bid，導致點擊錯誤的元素
- **已排序仍持續點擊**：Agent 在欄位已排序後仍然持續點擊欄位標題，無法感知當前的排序狀態
- **選單導航困難**：Agent 無法順利展開摺疊的選單層級，因 accessibility tree 中只有展開後的連結才可見
- **表單分頁困難**：Agent 無法理解多頁籤表單的結構，在錯誤的頁籤中填入本應在另一頁籤的欄位
- **幻覺操作**：Agent 使用不存在的函數或嘗試用名稱替代 bid
- **L3 理解失敗**：Agent 將 ticket 中的任務描述誤解為已完成的任務記錄，直接將 ticket 關閉

這些錯誤類型與 SaaS-Bench 中觀察到的部分模式一致（特別是「缺乏閉環驗證」與「狀態感知困難」），但 SaaS-Bench 的跨應用與長時距特性暴露了更多深層次的失敗模式。

**人類 baseline。** WorkArena++ 的人類 baseline 在 80% 以上。SaaS-Bench 沒有報告人類 baseline，但考慮到任務的真實性與嚴格審查過程，任務應該對人類專家是可解的。兩個 benchmark 都確認了一個基本前提：任務的限制主要來自 agent 的能力，而非任務設計的缺陷。

### 關鍵失敗模式的深入解讀

**級聯效應的數學本質。**

在長時距任務中，錯誤的級聯傳播可以形式化為一個累積概率問題。設一個任務有 $n$ 個順序步驟，每個步驟 $i$ 的獨立成功率為 $p_i$。則任務整體成功率為 $\prod_{i=1}^{n} p_i$。即使每個步驟的 $p_i = 0.99$（非常高），100 步的任務整體成功率也僅為 $0.99^{100} \approx 0.366$。實際中，$p_i$ 遠低於 0.99——agent 在複雜的 SaaS UI 中操作時，點錯按鈕、填錯欄位、誤解對話框等錯誤的發生頻率很高——因此 $n > 100$ 的長時距任務中，Resolved Score 極低是數學上的必然。

這說明了為什麼 SaaS-Bench 的 Resolved Score 如此之低，也說明了為什麼當前 CUA 需要根本性的架構改進而非僅是模型改進。

**案例分析：bof_133 的三系統協調任務。**

bof_133 是一個典型的跨應用任務：Agent 需要在 BigCapital（財務）、ERPNext（會計）與 Twenty CRM（客戶關係）三個系統之間協調運作，完成員工離職結算流程。任務涉及 200+ 步操作。

Claude Opus 4.6 在這個任務上的表現揭示了級聯效應的具體機制：

1. **早期迷失**（第 1–50 步）：Agent 花費過多時間在 BigCapital 中尋找正確的選單路徑，因為 SaaS 系統的選單結構（兩層以上的摺疊選單）不像 WebArena 的簡化頁面那樣直接可見
2. **倉促補償**（第 50–120 步）：意識到時間壓力後，agent 嘗試快速完成剩餘操作，開始跳過一些應該執行的步驟，直接進行後續操作
3. **錯誤累積**（第 120–200 步）：前期的跳過導致了後期依賴關係的斷裂。例如，因為沒有在 BigCapital 正確建立客戶記錄，ERPNext 的發票無法對應到正確的客戶
4. **最終失敗**（第 200+ 步）：Agent 雖然執行了 200+ 步操作，但關鍵的資料依賴鏈已經斷裂，最終只能獲得部分分數

這個案例的教訓是：在長時距任務中，**操作數量不等於任務進度**。一個 agent 可以執行 200 步操作，但因為早期路徑選擇錯誤而幾乎沒有實際進度。

**Chokepoint Error 的結構性特徵。**

Chokepoint error 不同於普通的執行錯誤。它具有三個特徵：(1) 發生在任務的關鍵資料依賴節點（如建立客戶記錄）; (2) 錯誤在執行中不可見（UI 顯示的結果看起來正確）; (3) 單一錯誤影響大量下游檢查點。

**案例分析：bof_019 的實體類型誤分類。**

bof_019 是一個採購付款任務，要求在 BigCapital 中建立一個名為「Arcturus Digital」的公司客戶，然後完成從採購單到發票到付款的完整財務流程。

關鍵的瓶頸點是：BigCapital 區分「個人客戶」（Individual Customer）與「公司客戶」（Company Customer）兩種實體類型。這兩種實體共用同一個建立介面，透過一個下拉選單選擇。Agent 需要理解「Arcturus Digital」是一個公司名稱，因此必須選擇公司客戶類型。

然而，大多數 agent 的行為是同時在「個人名稱」欄位填入「Elena Vasquez」（任務描述中出現的聯絡人姓名）和在公司名稱欄位填入「Arcturus Digital」。BigCapital 的 UI 在這種情況下會預設建立個人客戶。這個錯誤的可怕之處在於它**在操作過程中完全不可見**：

- 後續的資產負債表顯示「Elena Vasquez (Arcturus Digital)」與預期的 $55,000 金額
- Agent 讀取這個「看起來正確」的頁面後，將其解讀為操作成功
- Agent 甚至會在自己的推理追蹤中記錄「客戶建立成功」

但驗證時查詢「Arcturus Digital」這個公司名稱時，資料庫中沒有任何匹配的記錄——因為記錄被建立為個人客戶 Elena Vasquez，而非公司客戶 Arcturus Digital。

這個單一錯誤影響了 33 個檢查點中的 10 個（30% 的任務分數），即使該檢查點本身的權重只有 3%。六個模型中只有三個（Gemini、GPT-5.4、Qwen）成功將 Arcturus Digital 建立為公司客戶，但沒有一個模型能通過後續所有財務檢查——即使正確建立了客戶類型，發票金額、付款日期、客戶餘額仍然不正確。

**自我評估失敗的兩層問題。**

bof_023 案例揭示了當前 CUA 架構中的一個結構性缺陷：缺乏閉環驗證。Agent 可以識別錯誤、可以規劃修正、也可以執行修正——但它不會回到修正點去驗證修正是否真的生效。這與人類的行為形成鮮明對比：人類在修改一個日期後，自然會重新載入頁面確認。

bof_023 中 Claude Opus 4.6 的 210 步軌跡提供了詳細的證據：

- **第 124 步**：Agent 審查了剛建立的發票，正確識別出日期錯誤（2026-03-19 應為 2026-03-20）。其內部推理顯示：「Bill created with correct items... but date shows 19 Mar 2026 instead of 20 Mar 2026. Need to edit date to 2026-03-20.」Agent 規劃了修正並執行編輯操作
- **第 165 步**：經過一系列付款操作後，agent 的評估變為「Payment created successfully. Bill now shows 'Paid' status with Due Amount $0.00. Verdict: Success」
- **第 210 步**（終止）：Agent 自信宣告：「Bill created dated 2026-03-20 with 3 line items totaling $10,350.00, approved」

驗證結果直接反駁了這個總結：發票日期仍然是 2026-03-19。Agent 在第 124 步嘗試修正後，沒有重新檢查發票頁面確認修正是否生效，就直接假設修正成功了。最終的終止總結似乎是從計畫中的意圖（我打算設為 2026-03-20）而非實際觀察的結果（頁面顯示 2026-03-19）中提取資訊。

這個案例揭示了當前 CUA 架構中的一個結構性問題：**內部推理追蹤（evaluation、memory、next-goal）主要記錄意圖而非結果**。Agent 在 memory 中記錄「Bill shows Paid, due $0.00」，但這個 memory 是 agent 對自己操作的解讀，而不是來自對頁面實際狀態的重新讀取。

### pass@k 與方差分析

論文在 §4.2 報告了 pass@k 的結果：對於某些模型和任務，pass@5 是 pass@1 的 2–3 倍。這意味著模型其實「知道」如何完成任務，但每次執行時的隨機波動導致它無法穩定地做到。

這個發現對於 CUA 評估的設計有深遠影響。如果只看 pass@1，會得到「模型能力極低」的結論；但如果看 pass@5，會得到「模型具備潛力但缺乏穩定性」的結論。這兩個結論的實務意涵完全不同——前者暗示需要更強大的模型，後者暗示需要更好的執行架構（重試機制、檢查點恢復、集成策略）。

論文的方差分析進一步揭示了 Bifurcation Points 的存在：在某些決策點上，次優選擇會導致不可逆的路徑偏離，進而造成後續所有步驟失效。

**細部分析：bof_155 的模型內方差。** Claude Sonnet 4.6 在人力資源申訴工作流程（bof_155）上的三次運行結果：

| 運行 | 得分 | 通過檢查點 | 達到的階段 |
|------|------|-----------|-----------|
| Run 2 | 0.000 | 0 | 完全失敗，沒有通過任何檢查點 |
| Run 0 | 0.214 | 6 | 申訴類型、申訴記錄、員工調動、培訓計劃 |
| Run 1 | 0.679 | 19 | 完整完成 ERPNext 階段 + 兩筆費用記錄 + 三個 Twenty CRM 任務 |

Run 1 與 Run 2 之間的差距（0.679 vs 0.000）是質性的而非量性的——從「完全失敗」一躍到「實質完成」。論文特別指出，這種方差無法歸因於環境隨機性，因為環境在每次運行前都重置到完全相同的初始狀態。

**細部分析：bof_023 的跨模型與跨運行發散。**

| 模型 | Run 0 | Run 1 | Run 2 |
|------|-------|-------|-------|
| Claude Opus 4.6 | 0.80 | — | — |
| Qwen 3.6 Plus | 0.80 | 0.70 | 0.10 |
| Gemini 3.1 Pro | 0.10 | 0.10 | 0.70 |
| Doubao Seed 2.0 Pro | 0.10 | 0.10 | 0.10 |
| Kimi K2.5 | 0.70 | — | — |
| GPT-5.4 High | 0.30 | — | — |

幾個值得注意的模式：

1. **相同模型在不同 run 之間呈現大範圍擺盪**：Qwen 3.6 Plus 的最佳（0.80）與最差（0.10）相差 8 倍。Gemini 3.1 Pro 則呈現完全相反的模式
2. **某些模型的低分具有確定性**：Doubao Seed 2.0 Pro 在三輪運行中都只得到 0.10，暗示了一種確定性的失敗模式而非隨機方差
3. **最佳單次 score 匹配可能掩蓋不同的可靠性**：Opus 4.6 和 Qwen 3.6 Plus 的最佳 run 都是 0.80，但 Qwen 的方差（0.80 → 0.10）揭示了其最高表現不可重現

**Bifurcation Points 與路徑依賴。** 方差的根本原因在於長時距 SaaS 工作流程的路徑依賴性。在關鍵決策點——選擇先進入哪個應用、解讀歧義欄位、決定重試或放棄——agent 的隨機採樣差異會導致完全不同的執行軌跡。一旦 agent 走上次優路徑（例如在 bof_155 中花 50 步在一個不熟悉的 UI 元素上），剩餘的步驟預算可能不足以恢復。這種分岔動態解釋了為什麼方差在複合多應用任務上最高、在簡單單應用任務上最低：更多的決策點意味著更多的早期分歧有機會放大為截然不同的結果。

**對 CUA 評估方法的影響。** 這個發現挑戰了 CUA 領域的幾項慣例：

- **pass@1 的誤導性**：報告 pass@1 可能嚴重誤導——一個高方差模型可能因運氣在單次運行中表現出色或極差。多運行指標如 pass@k 與得分方差能夠提供更具資訊性的評估
- **對 CUA 部署的意涵**：在真實 SaaS 工作流程中觀察到的高方差表明，生產環境的 CUA 系統需要重試機制、集成策略或基於檢查點的恢復機制
- **pass@k 與 checkpoints 的互補性**：將 pass@k 分析與 checkpoint score 結合使用，可以消除單一運行或單一指標的偏差

## 總結、限制與未來方向

### 核心要點

SaaS-Bench 的核心貢獻可以歸納為三點：

第一，它揭示了一個令人不安但誠實的結論：**當前最強 CUA 在真實 SaaS 工作流程中的端到端成功率不到 4%**。這種表現與「公司用 CUA 取代人類知識工作者」的宏大敘事之間存在巨大鴻溝。如果一個模型在 106 個任務中連 4 個都無法完整完成，它就還沒有準備好用於任何真實世界的專業工作。

第二，它系統性地剖析了 CUA 在真實場景中的**根本性能力限制**——不僅是操作精確度問題，更是架構性問題：
- **缺乏閉環驗證**：Agent 無法確認自己的操作是否生效，導致錯誤無聲傳播
- **無法處理跨應用上下文**：在不同系統之間切換時，agent 無法保留前一個系統的操作上下文與資料依賴關係
- **缺乏對 SaaS 資料模型的深層理解**：Agent 停留在表面的 UI 互動層次，無法理解實體類型（個人 vs 公司）、外鍵關聯、業務規則等後端概念
- **路徑依賴與高方差**：長時距任務中的早期小決策偏差，會透過分岔點放大為截然不同的結果

第三，它提供了一個**可重現、可擴展的評估框架**：23 個 Docker 容器化的真實系統、106 個經過四階段嚴格審查的任務、三層驗證機制（State-Check、Content-Check、LLM-Judge）、兩種互補的評估指標（Resolved Score 與 Checkpoint Score）。這個框架不僅支援 14 個模型的系統性比較，也為後續 CUA 研究提供了標準化的評估環境。

### 驗證方法的詳細分類

SaaS-Bench 使用了三種驗證類別，每種包含多個子類型。以下是論文 Table 3 的完整分類：

| 驗證類別 | 子類型 | 說明 |
|----------|--------|------|
| State-Check | DB-Check | 查詢資料庫確認記錄、欄位或關聯存在 |
| | API-Check | 呼叫後端 API 確認系統狀態符合期望 |
| | Numeric-Threshold-Check | 驗證數值在指定容差範圍內 |
| | File-System-Check | 檢查執行過程中建立的檔案的存在性、格式或內容 |
| | Email/Message-Check | 驗證郵件或訊息已發送，收件人與內容正確 |
| Content-Check | Regex/String-Match | 提取的文字與正則表達式或精確字串比對 |
| | Doc-Extraction-Check | 從文件中提取結構化內容並驗證 |
| LLM-Judge | LLM-Judge (text) | 使用 LLM 評估開放式文字輸出（報告、評論、摘要） |
| | LLM-Vision-Judge (image) | 使用 VLM 評估圖像輸出（圖表、截圖、視覺產物） |

這個分類體系有一個重要的設計考量：**越靠前的驗證方法越可靠**。State-Check 是最可靠的（資料庫不會說謊），Content-Check 次之（regex 匹配可能因為格式差異而誤判），LLM-Judge 最不可靠（LLM 評估者本身存在偏誤）。SaaS-Bench 在任務設計時會優先使用 State-Check，只有在任務輸出本質上就是開放式的情況下（如「寫一份合理的報告」）才使用 LLM-Judge。

### Agent 行動空間

論文 Table 4 列出了 22 個可用操作。這些操作分為三類：

**瀏覽器 UI 操作**（14 個）：click、input、send_keys、scroll、select_dropdown、dropdown_options、upload_file、navigate、go_back、switch、close、wait、search、extract、find_elements、find_text、search_page、save_as_pdf

**檔案系統操作**（3 個）：read_file、write_file、replace_file

**終止操作**（1 個）：done

值得注意的設計決策是 **evaluate（原始 JavaScript 執行）被刻意禁用**。這是為了確保 agent 的行為具有可重現性——如果 agent 可以執行任意 JavaScript，那麼不同的初始隨機種子可能導致完全不同的執行結果。透過限制 agent 只能使用標準的瀏覽器 UI 操作，SaaS-Bench 確保了評估結果的穩定性與可比性。

### 限制

**任務設計的人為性。** 儘管 SaaS-Bench 的任務經過嚴格審查，但任務描述仍然是人為指定的——真實世界的使用者在操作 SaaS 時，不會有如此清晰的目標描述。這是所有 system-level benchmark 的固有局限。一個更真實的評估可能需要使用者以自然語言（而非結構化描述）提供任務目標，或直接從使用者行為記錄中提取任務。

**SaaS 系統的版本漂移與維護成本。** SaaS-Bench 使用 Docker 鎖定系統版本以確保可重現性，但這也意味著當開源 SaaS 系統發布新版本時，benchmark 會老化。23 個系統的容器映像需要定期更新以保持環境的時效性——這對維護團隊是一個顯著的運維負擔。論文沒有明確說明版本更新的計畫與頻率。

**評估成本的考量。** SaaS-Bench 的任務需要 Docker 部署 23 個系統。根據系統的複雜度，這可能涉及 10–30 GB 的硬碟空間與 8–16 GB 的記憶體需求。加上每次任務執行需要 100–400 步操作，單一模型的完整評估可能需要數小時甚至數天的計算時間。這使得大規模評估的成本相當高，可能限制了 SaaS-Bench 的廣泛採用。

**驗證器設計的潛在偏誤。** LLM-Judge 類別的驗證依賴於另一個 LLM 對 agent 輸出的評判，這引入了驗證器本身可能存在的偏誤。雖然論文使用規則型驗證（DB-Check、API-Check）來降低依賴，但對於開放式任務（報告品質、圖像理解），LLM-Judge 仍然是必要的。論文沒有深入分析 LLM-Judge 的可靠性——例如，不同的 LLM 作為 judge 是否會導致不同的排名結果。

**任務覆蓋範圍的取捨。** SaaS-Bench 強調質而非量：106 個任務經過嚴格審查，但數量遠少於 WorkArena++ 的 682 個。這種取捨意味著某些 CUA 能力的面向可能被低估或遺漏——例如，如果某個特定的 SaaS 操作模式在 106 個任務中沒有充分體現，評估結果可能無法反映 agent 在該模式上的真實能力。任務的領域分布也不是均勻的——有些領域（如 Business）的任務數量多於其他領域。

**非英語的適用性。** 當前 SaaS-Bench 的系統與任務以英文介面為主。這在一定程度上限制了 benchmark 對非英語 CUA 評估的適用性。不同的語言與文化背景下，SaaS 系統的 UI 佈局、欄位命名與業務邏輯可能有所不同。

**Oracle 機制與驗證器的耦合。** SaaS-Bench 的每個任務依賴對應的 verify.py 腳本進行自動化驗證，這意味著 oracle 機制的正確性直接決定了評估結果的可信度。如果 verify.py 中存在 bug（例如 DB-Check 的查詢邏輯錯誤、regex 匹配過於寬鬆），可能導致誤報（false positive）或漏報（false negative）。論文雖然經過四階段審查，但沒有報告 verify.py 本身的測試覆蓋率或可靠性分析。對於依賴 verify.py 進行訓練資料標註的後續研究而言，這個限制需要特別關注。

**Docker 依賴與可移植性。** 23 個 SaaS 系統各自需要獨立的 Docker 容器。雖然這確保了可重現性，但也意味著 SaaS-Bench 的部署依賴於宿主機的資源配置。某些系統（如 ERPNext 的 mariadb + nginx + backend 多容器架構）的啟動時間可能超過 5 分鐘，這在大量任務執行場景中會顯著增加總評估時間。此外，如果宿主機無法啟動 Docker（如某些雲端 notebook 環境），SaaS-Bench 就無法運作。

**評估模型的時效性。** SaaS-Bench 評估了 2026 年初的 14 個先進模型，但 CUA 領域的模型迭代速度極快。論文發表後數月內可能就有新模型在相同任務上表現大幅超越。這不是 SaaS-Bench 特有的問題，而是所有 system-level benchmark 都面臨的挑戰——benchmark 的設計時間點與評估結果的時效性之間存在固有矛盾。理想的因應方式是定期更新評估結果（例如每季或每半年），但這需要持續的運維資源投入，論文沒有說明是否有此規劃。

**對 Agent 架構差異的敏感度。** SaaS-Bench 使用統一的 browser-use 執行框架評估所有模型。這確保了公平比較，但也意味著架構上的差異（如不同的 planning 策略、memory 管理、error recovery 機制）被 browser-use 的統一抽象層掩蓋了。某些模型可能因其內部架構在 browser-use 之外的框架中表現更好，而 SaaS-Bench 無法捕捉這種差異。這是在公平性與真實性之間的必要取捨。

### 對 CUA 架構的啟示

SaaS-Bench 的失敗分析對未來 CUA 架構設計提供了明確的方向：

1. **閉環驗證（Closed-Loop Verification）** ：Agent 需要在執行的每個關鍵步驟後進行明確的驗證操作——重新讀取欄位、查詢資料庫、比較當前狀態與期望狀態——而不是假設操作已經生效。架構上，這意味著 agent 的執行循環應從「感知→推理→行動」擴展為「感知→推理→行動→驗證」，其中驗證步驟的輸出會回饋到推理步驟，形成一個閉環

2. **跨應用上下文管理（Cross-Application Context Management）** ：Agent 需要一個持久化的工作記憶，能夠在不同系統切換時保留上一個系統的操作上下文。具體來說，agent 應維護一個獨立的「任務進度狀態」資料結構，包含已完成的操作、已建立的實體（客戶、發票等）、這些實體的 ID 與欄位值，以及尚未滿足的依賴關係。當 agent 從 BigCapital 切換到 Twenty CRM 時，這個狀態資料結構應被保留和傳遞

3. **SaaS 資料模型理解（SaaS Data Model Understanding）** ：Agent 需要超越表面 UI 互動，理解 SaaS 應用背後的資料模型——客戶類型（個人 vs 公司）選擇的影響、會計科目結構對發票的約束、外鍵關聯對跨系統查詢的影響。這可能需要在 agent 架構中加入資料模型感知層，能夠從頁面結構推導後端資料模型的輪廓

4. **檢查點恢復機制（Checkpoint-based Recovery）** ：基於 SaaS-Bench 中觀察到的 Bifurcation Points，agent 應能在關鍵決策點自動儲存狀態，在進入死路時回溯到最近的檢查點。這類似於軟體開發中的 savepoint 概念，但在 CUA 環境中實現起來更困難，因為 UI 狀態的儲存與恢復涉及瀏覽器 DOM 狀態、cookie、localStorage 等多個層面

5. **重試與集成策略（Retry and Ensemble Strategies）** ：pass@k 的結果表明，多次執行的集成策略可以顯著提升 CUA 的可靠性。一個實用的部署策略可能是：對同一個任務執行 3–5 次，選擇 checkpoint score 最高或採用多數決的方式決定最終結果

6. **自我評估與偏誤校準（Self-Assessment and Calibration）** ：bof_023 案例揭示了 agent 內部自我評估的不可靠性。未來架構應包含一個獨立的評估模組，其評估結果應基於環境狀態的客觀觀測而非 agent 的主觀意圖。這可以是一個專門的驗證器模型，或一個使用不同 prompt 的評估 LLM

### 後續研究方向

SaaS-Bench 的出現將推動 CUA 研究的幾個方向：

- **CUA 專用架構設計**：目前 CUA 主要依賴通用 LLM + browser-use 框架，未來的 CUA 專用架構可能包含內建的狀態追蹤器、可區分意圖與結果的內部推理模組、以及自動化驗證循環。SaaS-Bench 的失敗分析為這種架構設計提供了具體的設計目標——例如，新的架構應能將 bof_023 的驗證失敗率降低至少 50%

- **細粒度的能力診斷**：SaaS-Bench 的加權檢查點體系可以進一步發展為能力剖面圖（Capability Profile），精確定位每個模型在哪些類型的操作上最容易出錯。例如，一個模型可能在「跨應用導航」上表現良好，但在「選擇正確的實體類型」上表現極差。這種細粒度的診斷可以指導有針對性的模型改進

- **CUA 訓練資料生成**：從 SaaS-Bench 的任務執行軌跡中提取高品質的訓練資料，用於微調 CUA 專用模型。SaaS-Bench 的 verify.py 提供了自動化的正確性標籤——它可以分辨哪些操作序列最終通過了驗證、哪些沒有——這使得大規模監督式學習成為可能

- **跨語言與跨文化適應性**：當前 SaaS-Bench 的系統與任務以英文介面為主，未來可以擴展到其他語言的 SaaS 生態系，或引入非英語的 SaaS 系統（如中國的釘釘、飛書、企業微信）

- **多模態 CUA 評估的深化**：SaaS-Bench 涵蓋了 32 個多模態任務，但多模態評估仍處於早期階段。未來可以設計更多需要跨模態推理的任務——例如，從一張發票掃描圖中提取金額、在 CRM 中建立對應的付款記錄、然後在財務系統中產生會計分錄

- **從評估到訓練的反饋循環**：SaaS-Bench 的 verify.py 不僅可以評估 agent，還可以產生正確性信號用於訓練。將驗證結果作為獎勵信號（reward signal）回饋給 agent 的訓練過程，可以形成一個從評估到訓練的閉環

### 個人觀點

SaaS-Bench 的價值不僅在於揭露 CUA 的當前限制，更在於提供了一個清晰的**能力進展指標**。從 WorkArena 到 WorkArena++ 再到 SaaS-Bench，CUA benchmark 的演進路線就是 increasing realism 的歷史：從合成環境到真實平台，從單一應用到跨系統協調，從短視野到長時距，從純文字到多模態。

Resolved Score 的 3.8% 不是一個令人沮喪的數字——它是一個誠實的基線。當這個數字在未來達到 10%、20%、50% 時，我們才能真正說 CUA 正在從實驗室走向辦公室。

我認為 SaaS-Bench 最重要的貢獻不在於它的實驗結果（雖然結果確實令人警醒），而在於它提供的**診斷能力**。一個只告訴你「你的模型得分是 X%」的 benchmark 是有用的，但一個能告訴你「你的模型在跨應用狀態追蹤上得了 Y 分、在實體類型選擇上得了 Z 分」的 benchmark 才是真正有價值的。SaaS-Bench 的加權檢查點體系——每個任務有多個檢查點、每個檢查點對應特定的能力——為 CUA 評估從「單一數字」進化到「能力剖面」奠定了基礎。

另一個值得深思的點是論文 §5.4 的「單次運行是否足夠」問題。在機器學習的傳統評估中，單次運行的結果被普遍接受為模型能力的估計。但 SaaS-Bench 的方差分析表明，在同一個模型中，單次運行的結果可能從「完全失敗」到「實質完成」——這是一個質性的差距，不是量性的誤差範圍。這個發現不僅挑戰了 CUA 領域的評估方法，也可能對更廣泛的 LLM agent 評估領域有啟發意義。

最後，SaaS-Bench 選擇的 23 個開源 SaaS 系統本身就是一個有價值的資源。這些系統涵蓋了從專案管理（OpenProject）到醫療（OpenEMR）到媒體（PhotoPrism）的廣泛領域，且全部可透過 Docker 部署。任何研究團隊都可以在自己的機器上複製整個評估環境——這在可重現性方面樹立了 CUA 評估的新標準。

有一點值得特別提出來討論：SaaS-Bench 與 TheAgentCompany 雖然都是 2024–2025 年間提出的真實環境 CUA benchmark，但兩者在設計哲學上有根本性的差異。TheAgentCompany 的任務偏向內部 API 操作與工具使用（例如透過 API 查詢資料庫、使用 curl 呼叫內部服務），而 SaaS-Bench 的所有操作都必須透過瀏覽器 UI，不允許直接操作後端。這兩個 benchmark 一起使用，可以更全面地評估 CUA 的能力剖面——一個評估瀏覽器 UI 操作，另一個評估 API/命令列操作。從這個角度看，目前還沒有一個 benchmark 能夠同時涵蓋這兩種操作模式，這是一個值得未來研究填補的空白。

從更宏觀的角度來看，SaaS-Bench 的出現也反映了 AI 評估領域的一個更深層的趨勢：**從 static benchmark 到 dynamic evaluation**。傳統的 machine learning benchmark 是靜態的——固定的測試集、固定的指標、固定的環境。但對於 agent 系統而言，靜態評估無法捕捉互動環境中的複雜動態。SaaS-Bench 的動態環境、長時距任務、多重檢查點驗證，代表了一種更接近真實部署條件的評估哲學。我認為這個趨勢將在未來幾年加速——2026 年可能是 CUA 評估從「static QA」轉向「dynamic evaluation」的轉折年。

總結來說，SaaS-Bench 是一篇定位清晰的論文。它不像有些 benchmark 論文那樣號稱「全面評估了 CUA 能力」，而是誠實地說：「我們只測了一件事——CUA 在瀏覽器 UI 層面操作真實 SaaS 系統的能力，而這件事已經夠難了。」這種聚焦與誠實，是 SaaS-Bench 與許多泛泛的 benchmark 論文的關鍵區別。對於任何正在打造 CUA 產品的團隊而言，SaaS-Bench 提供的不是一個可以貼在官網的「得分」，而是一份工程挑戰的清單——缺乏閉環驗證、跨應用上下文遺失、實體類型誤判——這些才是真正的瓶頸。

## 延伸閱讀

- **WorkArena**（Drouin et al., 2024, arxiv:2403.07718）：SaaS-Bench 最直接的前置工作，第一篇提出在真實企業平台上評估 web agent 的論文。包含 33 個原子級任務，在 ServiceNow 平台上執行。SaaS-Bench 在 Table 1 中明確與其對比，定位為從單一平台、短視野跨向多平台、長視野的關鍵改進。WorkArena 使用了與 SaaS-Bench 相同的 BrowserGym 環境架構。

- **WorkArena++**（Boisvert et al., 2024, arxiv:2407.05291）：WorkArena 的擴展版，將任務從 33 個擴展到 682 個，並引入了 L2（明確指令）與 L3（ticket + 知識庫）兩種難度層級以及五種技能類別（規劃與問題解決、資訊檢索、資料驅動決策與推理、複雜記憶、情境理解）。這是 SaaS-Bench 選定的 dependency paper，因其在企業 SaaS 評估領域最為接近。

- **WebArena**（Zhou et al., 2023, arxiv:2307.13854）：首個建構可執行網頁環境的 web agent benchmark，為後續工作奠定了環境建置、任務設計與驗證的流程範式。WebArena 提供了 190 個任務，涵蓋地圖、電子商務、維基、社交論壇等多樣網站，但其環境仍為自架而非真實 SaaS 系統。

- **OSWorld**（Xie et al., 2024, arxiv:2404.07972）：將 CUA 評估從網頁擴展到桌面作業系統，引入了多模態感知與開放式任務的挑戰。OSWorld 涵蓋了 369 個跨應用桌面任務，但主要聚焦於作業系統層級的操作（檔案管理、設定調整），而非 SaaS 專業工作流程。

- **Online-Mind2Web**（Xue et al., 2025, arxiv:2504.01382）：揭示了離線評估與線上評估之間的巨大差距，與 SaaS-Bench 的發現互相呼應。該論文指出，過去報告的許多 CUA 進展在脫離受控的離線設定後便消失了——這與 SaaS-Bench 關於現有 benchmark 系統性高估 CUA 能力的論點一致。

- **TheAgentCompany**（Xu et al., 2024, arxiv:2412.14161）：另一個近期提出的真實環境 CUA benchmark，與 SaaS-Bench 同樣關注企業工作場景。但 TheAgentCompany 側重於內部工具與 API 操作，而非 SaaS 瀏覽器操作。兩者可以形成互補：SaaS-Bench 評估瀏覽器操作的 CUA，TheAgentCompany 評估 API/工具操作的 CUA。

- **CocoaBench**（Hao et al., 2026, arxiv:2604.11201）：另一個近期提出的異質真實應用 CUA benchmark，強調在多元化真實應用中的評估。與 SaaS-Bench 同年發表，共同反映了 CUA 評估從合成到真實的轉向趨勢。
